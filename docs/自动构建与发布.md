# 自动构建与发布

工作流位于 `.github/workflows/release.yml`，使用 GitHub 托管的 Windows 2025 构建环境、MSVC、Windows SDK 和 .NET 10。官方 Actions 固定到具体提交；发布使用工作流自带的 GITHUB_TOKEN，无需配置个人令牌。

## 推送后会发生什么

| 操作 | 结果 |
|---|---|
| 推送 main | 构建和测试后更新 dev 预发布，保留当前版本 ZIP 和 SHA-256 文件 |
| 推送 v开头的版本标签 | 标签必须与项目版本完全相同，构建和测试后创建正式 Release |
| 向 main 提交 PR | 只构建、测试并上传 Actions 构件，不发布 |
| Actions 页面手动运行 | main 更新开发版；版本标签发布正式版；其他分支只验证 |

开发版不占用正式版 Latest 标记。正式版一经发布不覆盖附件；如需修复，应使用新版本号。相同标签的未完成草稿可以重试。main 构建发布前检查分支最新提交，旧构建不会覆盖新开发版。发布步骤在校验 ZIP 的 SHA-256 后才上传文件。

构建任务只有读取权限，发布任务单独申请 contents: write；只有本仓库 main 和版本标签能够进入发布任务。云端首次运行及仓库权限需要在推送后由实际 Actions 结果确认。

## 首次发布 0.2.3

在本地提交和 v0.2.3 标签均准备好后执行：

```powershell
git push origin main
git push origin v0.2.3
```

第一条触发开发版更新，第二条触发 0.2.3 正式发布。进入仓库 Actions 页面查看 Build, test and release，成功后在 Releases 页面下载 ZIP 和对应的 `.sha256` 文件。不需要提交 dist、build 或 bin 目录。

## 后续发布

1. 修改 `bridge/AgentStatusBridge.csproj` 的 Version，同时更新 `bridge/Transport.cs` 和 `plugin/AgentStatus.cpp` 中的版本字符串。
2. 按需新增 `docs/releases/v版本号.md`；没有该文件时，首次创建正式 Release 使用 GitHub 自动生成的说明。
3. 本地构建并测试，提交后创建同版本的 Git 标签，再推送分支和标签。

```powershell
./build.ps1 -SelfContained
./tests/Integration.ps1
./tests/Installation.ps1
./tests/ReleasePublishing.ps1
```

本机安装了 Visual Studio C++ 工具和 Windows SDK 时，构建脚本自动发现路径。自带工具链可使用 `-Toolchain`；SDK 位于其他位置时增加 `-WindowsSdk`。发布测试替换 gh 命令为内存模拟，不对 GitHub 执行写入。
